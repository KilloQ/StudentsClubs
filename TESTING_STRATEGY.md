# Тестовая модель MVP

## 1) Критические пользовательские сценарии
- Аутентификация: регистрация, вход, получение `auth/me`, обновление токена, logout.
- Каталог кружков: загрузка списка, фильтрация, сортировка, пагинация, открытие карточки.
- Доступ по ролям: студент/преподаватель/админ для защищенных маршрутов и CRUD действий.
- Операции с кружками: создание/изменение/удаление (с проверкой владельца или администратора).
- Работа с файлами: загрузка, выдача ссылки на скачивание, удаление.
- Интеграции: погода (штатный ответ, валидационные ошибки, деградация внешнего API).

## 2) Ключевые бизнес-правила и ограничения
- Доступ к управлению кружками только для преподавателя/админа.
- Изменять/удалять кружок может владелец либо администратор.
- Вступление в кружок только для студентов; нельзя вступить дважды.
- Нельзя вступить при закрытом наборе и при переполнении.
- Ограничения запроса каталога: `page>=1`, `1<=page_size<=50`, whitelist `sort_by/sort_order`.
- Загрузка файлов: контроль MIME-типа, запрет пустого файла, ограничение максимального размера.

## 3) Области повышенного риска
- **Аутентификация:** протухание access/refresh, корректный fallback на logout.
- **Роли/права:** обход frontend-guard без backend-проверок, несовпадение роли и `is_teacher`.
- **Файлы:** загрузка недопустимых типов, oversized payload, несанкционированный доступ к delete/download.
- **Внешние API:** таймауты, 429/5xx, неконсистентная структура ответа провайдера.

## 4) Структура тестирования
- Backend unit: `backend/tests/unit/` (быстрые сервисные тесты).
- Backend integration: `backend/tests/integration/` (эндпоинты + DB/валидация/статусы).
- Frontend unit/integration: `frontend/src/**/*.unit.test.ts(x)` и `*.integration.test.ts(x)`.
- E2E: `frontend/e2e/*.spec.ts` (сквозные бизнес-потоки и UX-сценарии).

## 5) Тестовая инфраструктура
- Backend test env: изолированная SQLite (`sqlite+aiosqlite:///:memory:`) на каждый тест.
- Очистка состояния: пересоздание схемы через фикстуру и отдельный session scope.
- Моки внешних зависимостей:
  - backend: monkeypatch для `ExternalWeatherService` и storage adapter;
  - frontend/E2E: перехват `fetch`/Playwright route для API и ошибочных ответов.
- Конфиги:
  - `backend/pytest.ini`
  - `frontend/vitest.config.ts`
  - `frontend/playwright.config.ts`

## 6) Метрики качества и соглашения
- Минимальное покрытие (контрольное):
  - Backend: не ниже 70% на `app/services` + `app/api`.
  - Frontend: не ниже 65% на `src/api`, `src/components`, `src/pages`.
- Разделение по скорости:
  - `unit` (секунды, без сети),
  - `integration` (локальная БД/рендер/роутинг),
  - `e2e` (полные сценарии UI).
- Нейминг:
  - `test_<feature>_<behavior>.py`
  - `<Feature>.<scope>.test.ts(x)`
  - `<flow>.spec.ts` для Playwright.

## 7) Итоговая проверка (Definition of Done)
- Подтверждено прохождение критических сценариев auth/catalog/CRUD/files/integrations.
- Подтверждено соблюдение ролей и запретов доступа (403/401/redirect).
- Подтверждена обработка валидационных ошибок (422/400) и серверных отказов (5xx/503).
