# Паспорт проекта и исходное состояние

## Паспорт

| Поле | Описание |
|---|---|
| Название | Student Clubs — система управления студенческими кружками |
| Репозиторий | [https://github.com/KilloQ/StudentsClubs](https://github.com/KilloQ/StudentsClubs) |
| Происхождение | Собственный проект автора репозитория; не форк |
| Назначение | Единый каталог кружков с записью студентов и инструментами преподавателя для организации занятий |
| Целевые пользователи | Студенты, преподаватели/руководители кружков, администратор |
| Команда | Один автор; самостоятельно выполняет разработку, тестирование, документацию и выпуск |
| Лицензия | Не выбрана по решению автора. Лицензия в репозитории отсутствует; права на код не предоставлены третьим лицам |

### Решаемая проблема

Информация о кружках, расписании и наборе может быть разрозненной, а учёт участников и посещаемости требует ручной работы. Приложение объединяет каталог, запись на кружки, управление расписанием и административные функции.

### Три основные функции

1. Каталог кружков с просмотром карточек, фильтрацией по категориям и записью студента.
2. Рабочее место преподавателя: управление кружками, участниками, расписанием и посещаемостью.
3. Управление пользователями и категориями каталога с разграничением прав по ролям.

Дополнительные реализованные возможности: объявления, вложения к кружкам, профили пользователей и получение погодных данных через внешний API.

### Технологический стек

Исходники организованы по отдельным приложениям `backend/` и `frontend/`; верхнеуровневый каталог `src/` не используется. Тесты расположены рядом с соответствующим приложением. Это отражено в документации без перемещения работающего кода.

### Точки входа

- Backend: `backend/app/main.py`; контейнер запускается через `backend/entrypoint.sh`, который вызывает `python -m app.db.init_db` и `uvicorn app.main:app`.
- Frontend в разработке: `frontend/src/main.tsx` через Vite; production-образ собирается `frontend/Dockerfile` и обслуживается Nginx.
- Локальный полный запуск: `docker compose up -d --build` из корня.

### Внешние зависимости и хранение данных

- PostgreSQL хранит пользователей, роли, кружки, категории, расписание, членство, посещаемость, refresh-токены, объявления и метаданные файлов.
- MinIO хранит объекты файлов и изображений; в БД остаются ссылки/метаданные.
- Внешний OpenWeather API используется погодным endpoint. API-ключ задаётся через `EXTERNAL_WEATHER_API_KEY`; без ключа внешняя функция ограничена.
- В тестах backend используется SQLite in-memory; frontend использует Vitest/Testing Library, а E2E — Playwright.
- Docker volumes `pgdata` и `miniodata` сохраняют данные между перезапусками Compose.

### Конфигурация

Backend загружает настройки из переменных окружения и `.env` (`backend/app/core/config.py`). Для Compose локальный пример находится в `backend/.env.example`; файл `backend/.env` не коммитится. Для публичных URL и параметров Vite используется корневой `.env` и `/.env.example`. Секреты и реальные ключи в репозиторий не добавляются.

## Первые наблюдения и черновики issues

Следующие наблюдения требуют регистрации issues в GitHub с метками `bug` или `question`; при проверке репозитория открытых issues не найдено:

1. **Bug:** проверки backend/frontend в CI закомментированы, но deploy job зависит от их имён; конфигурация CI/CD не обеспечивает ожидаемую проверку перед развёртыванием.
2. **Bug:** production-конфигурация имеет небезопасные значения по умолчанию (`SECRET_KEY`, учётные данные MinIO, демонстрационные пользователи); необходимо требовать явные секреты для production и исключить использование демонстрационных паролей вне локального окружения.
3. **Bug:** `test_admin_category_crud_and_rename_updates_clubs` удаляет категорию, затем передаёт её ID в reorder и ожидает HTTP 200, тогда как endpoint требует точное совпадение ID с существующим набором категорий. Последний запуск: тест упал с HTTP 400.
4. **Bug:** frontend integration test LandingPage падает при рендере без `AuthProvider` (`useAuth must be used within an AuthProvider`); нужно проверить test wrapper/provider setup.
5. **Question:** миграции схемы выполняются ad hoc в `init_db.py`, при этом отдельного каталога Alembic migrations в репозитории нет; нужно решить, переводить ли изменение схемы на версионируемые миграции.
6. **Bug:** `npm run lint` завершается с тремя ошибками `no-unused-vars` в `Logo.tsx`; устранить ошибки перед включением lint в CI.

Issue product и эти шесть issues ещё не созданы. Сообщение npm audit также требует triage. Публичные действия в GitHub и настройка защиты ветки выполняются отдельно в интерфейсе GitHub.

## Выполнимость и план

### Риски

| Риск | Вероятность | Последствия | Снижение |
|---|---|---|---|
| Недостаток времени у единственного участника | Средняя | Сокращение объёма или задержка лабораторных работ | Уточнять объём в начале каждой работы, планировать небольшие PR и резерв времени |
| Незнакомые детали async SQLAlchemy, Docker и объектного хранилища | Средняя | Ошибки интеграции и длительная отладка | Сохранять воспроизводимый Compose-запуск, покрывать API unit/integration тестами |
| Зависимость погоды от ключа и доступности внешнего API | Средняя | Функция недоступна офлайн или при исчерпании лимита | Ключ через окружение, тесты с mock, погода не является критическим путём |
| Секреты/учётные данные по умолчанию в демонстрационной конфигурации | Средняя | Риск при ошибочном развёртывании | Использовать только локальные примеры, требовать отдельные production secrets |
| Лицензия не выбрана | Низкая для локального курса, высокая для внешнего повторного использования | Неясные права пользователей на использование кода | До распространения зафиксировать решение автора о лицензировании |
