# Валидация требований и изменения

## Исходная проверка

В лабораторной работе 1 требования описаны как текущее понимание автором проекта и ещё не согласованы с преподавателем. Формальная валидация критериев приёмки, сквозные идентификаторы и регистрация запросов на изменение запланированы на ЛР-2.

| Проверка | Результат |
|---|---|
| Определены основные роли | Да: посетитель, студент, преподаватель, администратор |
| Основные функции сопоставлены с реализацией | Да: см. [паспорт и карту функций](./00-project.md#карта-функций) |
| Требования имеют измеримые критерии приёмки | Частично; требуется уточнение в ЛР-2 |
| Требования согласованы с преподавателем | Нет |
| Есть product issue | Нет; issue требуется создать в GitHub |
| Изменения требований зарегистрированы как CR | Нет; нумерация начинается в ЛР-2 |

## Черновики наблюдений для регистрации issues

При первичном анализе GitHub issues отсутствовали. Ниже подготовлены шесть тем; после регистрации нужно заменить статусы на ссылки и проставить репозиторные метки `bug`/`question`.

| Тема | Тип/метка | Основание | Ожидаемое решение |
|---|---|---|---|
| CI job’ы выключены, deploy зависит от них | bug | `.github/workflows/ci-cd.yml`: jobs тестов закомментированы, deploy использует их имена в `needs` | Включить backend/frontend проверки и проверить условия deploy |
| Демонстрационные секреты и пользователи | bug | Конфигурация содержит development defaults, а инициализатор создаёт известные пароли | Разделить локальные defaults и production-конфигурацию, запретить небезопасные production значения |
| Тест сортировки категорий использует уже удалённый ID | bug | `test_admin_category_crud_and_rename_updates_clubs` ожидает HTTP 200 после отправки несуществующей категории; фактический ответ API — HTTP 400 | Согласовать тест с ожидаемой валидацией endpoint либо изменить требование к reorder |
| Стратегия версионирования схемы | question | В `init_db.py` есть ad hoc `ALTER TABLE`, отдельные ревизии Alembic отсутствуют | Решить, нужна ли миграция схемы на версионируемые Alembic revisions |
| LandingPage integration test не предоставляет AuthProvider | bug | Рендер теста падает с `useAuth must be used within an AuthProvider` | Настроить общий test wrapper или явно обернуть тест provider’ом |
| ESLint находит неиспользуемые переменные | bug | `npm run lint` завершается с тремя ошибками в `Logo.tsx` | Удалить ненужные присваивания или корректно использовать переменные |

## Правило последующей валидации

На ЛР-2 каждому утверждённому требованию присвоить уникальный идентификатор `UR-n`, `FR-n`, `NFR-n`, а тесту — `T-n`. Для замечаний преподавателя завести issue; изменение принятого требования регистрировать как `CR-n`, фиксируя причину, затронутые требования и связанные тесты. Не считать требование принятым до согласования его критерия приёмки.
